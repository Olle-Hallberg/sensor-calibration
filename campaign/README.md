# K96 calibration pipeline

Calibrates the K96 sensor's optical readings into CO2/CH4 concentration
estimates. This is the middle stage of a bigger pipeline:

```
jsonl file  -->  raw CSV  -->  [THIS: predict CO2/CH4]  -->  analysis/plots
            (already built)                                (built separately)
```

## What's in this folder

| Path | What it is |
|---|---|
| `cont_dev_raw/`, `thesis_raw/` | Raw calibration data from the two collection campaigns. Source of truth - don't edit. |
| `harmonize_pool.py` | Builds `pooled_data.csv` from the two raw sources (unit harmonization, the per-session timestamp fix, sensor-glitch interpolation, etc.). |
| `pooled_data.csv` | The harmonized training set. Generated by `harmonize_pool.py` - checked in so you don't have to rebuild it unless the raw data changes. |
| `production_pipeline.py` | Trains the CO2/CH4 models + the envelope check, and saves them to `k96_calibration_pipeline.joblib`. Also the single-reading `predict()` / batch `predict_batch()` API. |
| `k96_calibration_pipeline.joblib` | The trained model artifact. Generated by `production_pipeline.py`. This is what `process_log_csv.py` loads - **training happens once, not per prediction run.** |
| `process_log_csv.py` | The actual day-to-day entry point: takes a raw field-log CSV, outputs the same CSV with `pred_co2_ppm`, `pred_ch4_ppb`, and data-quality flags appended. |
| `convert_sd_card_log.py` | Converts an SD-card flight recording (`metadata_noNN.log` + `sensor_data_noNN.csv`) into the raw field-log CSV schema `process_log_csv.py` expects. Only needed for SD-card recordings - the live-logged CSV format doesn't need this step. |
| `model_development/` | The scripts and intermediate results from developing the model (concentration-response curve, environmental correction, physical-vs-GBM comparison, holdout robustness checks). Reference/reproducibility only - **not needed to run the pipeline.** See its own notes below. |

## One-time setup in VSCode

1. Open this folder in VSCode (`File > Open Folder...`, select `campain`).
2. Install the **Python extension** if you don't have it (VSCode will usually prompt you).
3. Select the Python interpreter: press `Cmd+Shift+P` -> `Python: Select Interpreter` -> pick the conda environment that has `pandas`, `numpy`, `scipy`, `scikit-learn`, and `joblib` installed. (`.vscode/settings.json` already points VSCode at conda as the environment manager.) If you don't have such an environment yet:
   ```bash
   conda create -n k96calib python=3 pandas numpy scipy scikit-learn joblib
   conda activate k96calib
   ```
4. Open a terminal in VSCode (`` Ctrl+` ``) - it should already be in this folder and using the selected interpreter. All commands below assume you're running from `campain/` (not from inside `model_development/`).

## Running the pipeline

### Step 1 - rebuild the training data (only if the raw data changes)

```bash
python3 harmonize_pool.py
```
Regenerates `pooled_data.csv`. Skip this unless `cont_dev_raw/` or `thesis_raw/` changed - the checked-in `pooled_data.csv` is already current.

### Step 2 - train the model (only once, or after Step 1 changes the training data)

```bash
python3 production_pipeline.py
```
Trains the CO2/CH4 models and the envelope check, saves `k96_calibration_pipeline.joblib`, and runs a couple of demo predictions so you can see the output shape. **You do not need to run this before every prediction** - only when the training data has actually changed.

### Step 3 - predict on a field CSV (the normal day-to-day operation)

```bash
python3 process_log_csv.py path/to/field_log.csv path/to/output.csv
```
Loads the already-trained model (no retraining) and writes `output.csv`: the input file unchanged, plus `pred_co2_ppm`, `pred_ch4_ppb`, `ch4_reliable`, `ch4_warning`, `in_envelope`, `feature_out_of_range`, `envelope_violations`. Run this on as many field files as you like - each run is independent and fast, since training already happened in Step 2.

A row only gets a prediction if it has real sensor data, a plausible pressure/temp reading, and - field-firmware-specific - `data.pressureStateName == 'MEASUREMENT'` (the chamber is holding a stable, settled sample). This is deliberately NOT `data.mode == 'MEASUREMENTS'` - that broader field covers the whole pressure-cycling sequence (prepressurization, compression, air exchange, *then* measurement), and the optical sensor keeps reporting a nonzero signal through all of those sub-phases even though the chamber's contents are still actively changing. Checked on real field data: of 13,098 rows with `mode=='MEASUREMENTS'`, only 606 (4.6%) were actually in the settled `MEASUREMENT` sub-phase. Everything else is kept in the output with blank prediction columns rather than guessed at.

To run it on multiple files from VSCode's terminal:
```bash
for f in /path/to/field_logs/*.csv; do
  python3 process_log_csv.py "$f" "predicted_$(basename "$f")"
done
```

#### Optional: one averaged prediction per MEASUREMENT period

`output_csv` and `--periods-output` are both optional, but at least one must be given - pick either or both:

```bash
# per-row only (output_csv alone - same as Step 3 above)
python3 process_log_csv.py path/to/field_log.csv path/to/output.csv

# periods only (omit output_csv, give --periods-output instead)
python3 process_log_csv.py path/to/field_log.csv --periods-output path/to/periods.csv

# both
python3 process_log_csv.py path/to/field_log.csv path/to/output.csv --periods-output path/to/periods.csv
```
`--periods-output` writes a second CSV, one row per contiguous `pressureStateName == 'MEASUREMENT'` period in the file. Within each period, only the rows with a prediction are averaged (features first, then a single prediction on the averaged reading - not an average of per-row predictions), so a short glitch in the middle of an otherwise-good period doesn't spoil it. Columns: `period_start`, `period_end`, `n_rows_total`, `n_rows_valid` (how many of the period's rows actually went into the average), the averaged features, and the same prediction/flag columns as the per-row output. A period with zero valid rows is skipped entirely.

Note that periods can be very short (a handful of rows, or even one) if the chamber only briefly reaches the `MEASUREMENT` sub-phase rather than holding it - the output doesn't filter these out, so treat `n_rows_total`/`n_rows_valid` as a signal for how much to trust a given period.

### Optional: converting an SD-card recording first

If a flight was recorded to an SD card instead of being logged live, it comes
as two files (`metadata_noNN.log` + `sensor_data_noNN.csv`) in a different,
more compact schema - convert it to the live-logged schema before running
Step 3:

```bash
python3 convert_sd_card_log.py path/to/metadata_noNN.log path/to/sensor_data_noNN.csv path/to/converted.csv
python3 process_log_csv.py path/to/converted.csv path/to/output.csv --periods-output path/to/periods.csv
```

What it does and doesn't reconstruct, briefly (full detail, including how
each claim was checked, is in the script's own docstring):

- Column names, codes, and units differ from the live schema (e.g.
  `pressure_state` is a numeric code, not a string; `PP2` turned out to be
  `chamberPressureBar` under another name - confirmed byte-for-byte
  identical, not just correlated). All verified against a live-logged file
  before being treated as equivalent, not assumed from naming alone.
- The SD card's `HH:MM:SS` is **elapsed time since the recorder started**,
  not wall-clock time - it has to be anchored to a real timestamp. The
  anchor baked into the script (`ANCHOR`) was derived empirically (by
  matching the cadence of MEASUREMENT-period timing against a known live
  recording of the same flight) and is **specific to that one recording's
  power-on time**. Converting a different `noNN` recording needs a
  freshly-derived (or operator-provided) anchor - don't reuse `ANCHOR`
  blindly, the script will silently produce wrong timestamps if you do.
- A handful of columns (the 8 individual `thermal_errorN` fields, and the
  two `captured_errors_*_hex` halves) couldn't be verified against the live
  schema's equivalent combined field, so they're carried through under
  their own `sd_`-prefixed names instead of a guessed `data.*` target.
  `data.controller` (a string like `"MAIN_MCU_READY"`) isn't reconstructed
  at all - only one example value was available, not enough to decode it.

None of this affects Step 3's predictions either way - `process_log_csv.py`
only ever reads the handful of columns it actually needs, all of which are
in the verified set.

### Debugging in VSCode

Each script has a `if __name__ == "__main__":` block, so you can just hit the
Run/Debug button (▶) on `process_log_csv.py` or `production_pipeline.py` directly,
or set breakpoints and use `Run > Start Debugging` (F5) - VSCode's default
"Python File" debug config works without any extra setup.

## Things worth knowing before trusting the output

- **CH4 predictions are flagged unreliable on every row** (`ch4_reliable: False`, with a warning explaining why) - the training data never varied CH4 and CO2 independently, so this number tracks CO2 through the trained gas ratio, not a validated CH4 response. Don't build anything on it without first getting decoupled-gas calibration data.
- **`in_envelope: False` means "treat this prediction with caution,"** not "discard it" - it's the OR of two different checks: (1) a single feature outside anything ever trained on, or (2) the joint combination of features being novel even though each one individually is in-range. Check (2) is expected to fire on most field data (the lab's experimental design and real field conditions are different joint distributions) and `in_envelope` alone doesn't tell you which one happened - **`feature_out_of_range`** isolates just check (1), the rarer and more serious signal. Checked on real field data: 100% of predictions failed `in_envelope`, but only ~33% also had `feature_out_of_range: True`.
- Rows with no sensor data (housekeeping/event rows) or an unconfirmable pressure/temp glitch get **blank predictions, not interpolated ones** - unlike training, field data can't be visually verified as an artifact vs. a real reading, so this pipeline doesn't guess.

## About `model_development/`

These scripts document how the production model's design was arrived at -
the concentration-response curve, the T/P/RH environmental correction, why a
per-source gain term was needed, why a GBM was chosen over the physics-based
model for the final pipeline, and the holdout-robustness checks that
validated each step. They're kept for reference and reproducibility, not
because the pipeline needs them. They read `pooled_data.csv` from one level
up (`../pooled_data.csv`) and are run from inside `model_development/`:
```bash
cd model_development
python3 fit_joint_model.py        # physics-based model + holdout eval
python3 fit_gbm_comparison.py     # physics-based vs GBM, same holdout
```
